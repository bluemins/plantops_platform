# PlantOps

Multi-tenant SaaS platform for RO / packaged-drinking-water plants. Project brief and rules: [CLAUDE.md](CLAUDE.md).

## Who is who

| Who | What they are | Where they log in | How |
|---|---|---|---|
| **super_admin** | PlantOps operator (you). Creates plants, sets each plant's plan and modules, creates plant owners. Sees all plants. | `/super/login` | Email + password |
| **tenant_admin** (plant owner) | Owner of one plant. Adds and manages their own staff, sees read-only summaries of every module their plant has. | `/login` | Plant code + username + **password** |
| **Staff** (lab technician, store keeper, maintenance technician) | Work in their own module(s) only. A person can hold more than one role. | `/login`, or the module's own link | Plant code + username + **6-digit PIN** |

Each plant only ever sees its own data. The database enforces this, not just the screens (see CLAUDE.md).

### Plants, plans and modules
- A **plant** (tenant) has a **plant code** (e.g. `SAMPLEAQUA`). Everyone at that plant types it at login, and the
  phone remembers it after the first time.
- The plant's **plan** (set by super_admin) decides which **modules** are switched on and the limits, e.g.
  maximum users.
- A user can open a module only if it is switched on for the plant **and** their role allows it. The owner can
  open every switched-on module, read-only.

## Creating users

New users always get a **temporary** password or PIN. It is generated by the system and shown **once** to
whoever created the user. They must replace it with their own the first time they log in.

### super_admin: new plant + its owner
1. Log in at `/super/login`.
2. Fill in **New plant**: plant code, plant name, plan name, max users, renewal date, modules, and the owner's
   name and username (mobile is optional).
3. Click **Create plant**. A yellow box shows **plant code, username and temporary password**. Send these to the
   owner. They are not shown again.
4. To add a second owner later: open the plant → **Owners** → **Add owner**.

### tenant_admin (owner): new staff member
1. Log in at `/login` with plant code + username + password.
2. **Manage users** → **Add a user**: name, username, mobile (optional), and one or more roles.
3. Click **Add user**. A yellow box shows the **temporary 6-digit PIN**. Give it to the staff member. Choosing the
   *Owner* role makes it a temporary password instead.
4. The staff member logs in with plant code + username + PIN, then sets their own PIN.

The plan's **max users** is enforced. When the limit is reached, disable someone or ask PlantOps to raise it.

## Resetting passwords and PINs

| Who forgot | Who resets it | How |
|---|---|---|
| **Staff PIN** | Their plant owner | **Manage users** → **Reset PIN** on that person. A new temporary PIN is shown once. This also unlocks them and logs them out everywhere. |
| **Owner password** | super_admin | `/super` → open the plant → **Owners** → **Reset password**. A new temporary password is shown once. |
| **super_admin password** (known) | super_admin | `/super` → **Change password**. |
| **super_admin password** (forgotten) | Whoever has the server | In the project folder: `pnpm super:set-password` (or `pnpm super:set-password -- other@email`). Type the new password twice; nothing is shown while typing. All super_admin sessions are logged out. |
| **Changing your own** PIN/password | Anyone logged in | Home → **Change PIN / password**. Other phones/browsers you're logged in on are logged out. |

**Locked out?** 5 wrong tries lock an account for 15 minutes. The owner can **Unlock** a staff member straight
away from **Manage users**.

**Disabling** a user (owner: **Disable**) logs them out of the platform at once. Any module they have open loses
access within about 5 minutes. Users are never deleted, so the audit trail stays intact.

## Links (local development)

| What | Link |
|---|---|
| Plant login (owners + staff) | http://localhost:3000/login |
| super_admin | http://localhost:3000/super/login |
| Lab Records (placeholder module) | http://localhost:3001 |
| Floor Stock (placeholder module) | http://localhost:3002 |

The module links are served by `apps/dev-module`, a **development-only placeholder** that does the SSO side
exactly like a real module will. The real modules replace it from Phase 3. Opened directly without logging in, a
module shows a "go to PlantOps login" page. Automatic login when opening a module link directly comes in
Phase 2.

These `localhost` links work in this computer's browser, including Windows browsers on the same machine. They
do not work from a phone. Phone access needs the app deployed to a real address, or a local network setup.

## Layout
- `apps/platform`: platform shell (login, plants, plans, users/roles, SSO for modules)
- `apps/dev-module`: development-only placeholder modules (SSO receiver)
- `packages/auth`: token verification + access rules, used by every module
- `packages/db`: database helpers (`withTenant`, migrations)
- `packages/types`: shared types (roles, modules, plan, token)
- `packages/ui`: shared mobile-first UI pieces

## First-time setup (this machine)
Needs Node 22+ and a local PostgreSQL.

```bash
corepack enable pnpm
pnpm install
./scripts/setup-local-db.sh   # once: creates DB logins + databases, writes .env (asks for sudo)
pnpm db:migrate               # creates/updates tables
pnpm db:seed                  # creates the first super_admin and registers modules from .env
```

## Everyday commands
```bash
pnpm dev          # platform on :3000 + placeholder modules on :3001 / :3002
pnpm test         # all tests, against the separate plantops_test database
pnpm typecheck
```

## Registering a module (for SSO)
Add to `.env`, then run `pnpm db:seed`:
```
MODULE_URL_LAB_RECORDS=http://localhost:3001
MODULE_SECRET_LAB_RECORDS=<long random string, e.g. openssl rand -hex 32>
```
To check the full handoff against `pnpm dev` (login → one-time code → exchange → verify → reused code refused):
```bash
scripts/sso-smoke.sh PLANTCODE username PIN-or-password lab_records
```
